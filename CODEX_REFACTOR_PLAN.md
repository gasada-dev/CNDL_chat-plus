# CNDL\_chat+ — план рефакторинга и укрепления существующего проекта

> Этот документ предназначен для Codex.
>
> Цель работы — улучшить качество, безопасность, архитектуру, производительность, тестируемость и документацию уже существующего функционала CNDL\_chat+.
>
> **Запрещено добавлять новые пользовательские функции, которых сейчас нет в моде.**
>
> Работа должна сохранить текущее поведение мода, текущий интерфейс, формат основных настроек и совместимость со старыми конфигурациями.

---

# 1. Главная цель

Не расширять набор функций, а привести существующий проект в состояние, при котором:

- существующие функции работают стабильнее;
- пользовательские настройки невозможно легко потерять;
- входные данные тщательно проверяются;
- серверные команды формируются безопасно;
- код проще читать и изменять;
- каждый класс имеет понятную ответственность;
- логика не дублируется;
- тяжёлые операции не выполняются в render callback;
- основные алгоритмы покрыты тестами;
- Codex быстро понимает устройство проекта;
- будущие изменения можно добавлять без переписывания больших классов;
- ошибки одной подсистемы не ломают весь мод.

# 4. Критические правила работы Codex

## 4.1. Не выполнять весь план сразу

Каждый этап должен быть отдельным логическим изменением.

Перед началом этапа Codex обязан:

1. Изучить затрагиваемые классы.
2. Найти все места их использования.
3. Зафиксировать текущее поведение тестами или документацией.
4. Составить короткий план.
5. Изменить только одну подсистему.
6. Запустить сборку и тесты.
7. Перечислить изменённые файлы.
8. Описать риски.

## 4.2. Сначала зафиксировать поведение

Перед рефакторингом алгоритма нужно создать characterization tests.

Нельзя сначала переписать алгоритм, а потом писать тест под новую реализацию.

Тесты должны фиксировать текущее ожидаемое поведение:

- распознавание каналов;
- маски автоответчика;
- маски чёрного списка;
- защита от повторов;
- миграции конфигурации;
- parsing `/clan lookup`;
- сравнение версий;
- формирование серверных команд.

## 4.3. Не смешивать рефакторинг и новые возможности

В одном PR нельзя одновременно:

- перемещать классы;
- менять UI;
- менять алгоритм фильтрации;
- менять формат конфигурации;
- добавлять новую функцию.

Один PR должен решать одну понятную проблему.

## 4.4. Сохранять совместимость

Обязательно сохранить:

- MOD ID:

```text
gasada_chat_responder
```

- имя конфигурации:

```text
gasada-chat-responder.json
```

- клавишу F8 по умолчанию;
- существующие поля JSON;
- существующие значения `ChatChannel`;
- текущие префиксы по умолчанию;
- максимум из трёх периодических сообщений;
- правило «первое совпадение побеждает»;
- существующие серверные команды;
- существующий внешний вид без отдельной задачи на UI;
- существующую механику проверки обновлений.

## 4.5. Не скрывать ошибки

Запрещено:

```java
catch (Exception ignored) {
}
```

Допустимо подавлять ожидаемую ошибку только с поясняющим комментарием и debug-логом.

Каждая ошибка должна:

- либо возвращаться вызывающему коду;
- либо логироваться;
- либо отображаться пользователю;
- либо быть явно признана безопасной и ожидаемой.

# 8. Этап 2 — укрепление конфигурации

## Проблема

`ResponderConfig` содержит много публичных изменяемых полей, а `ConfigManager.load()` при любой ошибке возвращает настройки по умолчанию.

При повреждении JSON пользователь может временно увидеть пустую конфигурацию и случайно перезаписать старый файл.

## Требуемые изменения

### 8.1. Backup повреждённого файла

Если JSON невозможно прочитать:

1. Не удалять исходный файл.
2. Создать копию:

```text
gasada-chat-responder.broken-<timestamp>.json
```

3. Записать подробную ошибку в лог.
4. Загрузить безопасную конфигурацию по умолчанию.
5. Не перезаписывать повреждённый файл автоматически до явного сохранения пользователем.

### 8.2. Версия схемы

Добавить поле:

```java
public int schemaVersion;
```

Не удалять старые поля.

Текущий config без `schemaVersion` считать версией 0.

Создать последовательные миграции вместо скрытых проверок внутри одного большого `sanitize()`.

Пример:

```java
interface ConfigMigration {
    int fromVersion();
    int toVersion();
    void migrate(ResponderConfig config);
}
```

### 8.3. Разделить обязанности

`ResponderConfig.sanitize()` сейчас одновременно:

- восстанавливает null;
- мигрирует старые поля;
- удаляет дубликаты;
- исправляет значения;
- заменяет старые стандартные правила.

Разделить на:

```text
ConfigMigration
ConfigSanitizer
ConfigValidator
```

### 8.4. Атомарное сохранение

Сохранить текущий подход:

```text
temporary file → move → основной файл
```

Дополнительно:

- удалять старый `.tmp` перед новой записью;
- логировать fallback с `ATOMIC_MOVE`;
- удалять временный файл после неудачной операции;
- сериализовать JSON до начала файловой записи;
- не оставлять повреждённый основной файл;
- при возможности синхронизировать запись перед move;
- возвращать подробный результат, а не только `boolean`.

Пример:

```java
public record ConfigSaveResult(
        boolean success,
        String userMessage,
        Throwable error
) {
}
```

### 8.5. Валидация загруженных данных

UI-валидации недостаточно.

Config может быть изменён вручную, поэтому проверять данные нужно после загрузки и перед использованием.

Проверять:

- Minecraft-ники: `[A-Za-z0-9_]{1,16}`;
- Discord-ники: разрешённый Unicode-набор, максимум 32;

# 9. Этап 3 — общая нормализация и маски

## Проблема

- Discord распознаётся отдельными регулярными выражениями в нескольких классах.

## хардкодаТребуемые классы

### `ChatTextNormalizer`

```java
public final class ChatTextNormalizer {
    private static final Pattern WHITESPACE = Pattern.compile("\\s+");

    public String normalize(String text) {
        // единая реализация
    }
}
```

Требования:

- `Locale.ROOT`;
- trim;
- схлопывание пробелов;
- безопасная работа с null через явный контракт;
- не изменять исходную строку;
- не удалять пунктуацию;
- не менять существующую семантику.

### `WildcardMatcher`

Поддержать два уже существующих режима:

```java

CONTAINS_MATCH
```

Пример:

```java
public final class CompiledWildcard {

    private final Pattern pattern;

    public boolean matches(String normalizedText) {

    }
}
```

Не компилировать regex на каждое сообщение.

Перекомпилировать только:

- после загрузки config;
- после сохранения правил;
- после изменения списка muted words.

## Критерии готовности

- Семантика масок не изменилась.
- Нет дублирования glob-конвертера.
- Нет `String.matches()` для постоянного Discord pattern.
- Нет `Pattern.compile()` внутри обработки каждого сообщения.
- Все варианты покрыты тестами.

# 22. Логирование

## Категории сообщений

Использовать понятные префиксы:

```text
[CONFIG]
[CHAT]
[FILTER]
[RESPONDER]
[FRIENDS]
```

## Уровни

### ERROR

- config невозможно сохранить;
- обязательная инициализация не удалась;
- критическая ошибка runtime.

### WARN

- пропущено невалидное значение config;

- очередь lookup получила недопустимое значение;
- временный файл не удалось удалить;

### INFO

- мод инициализирован;
- config мигрирован;
- обнаружено обновление.

### DEBUG

- фильтр скрыл сообщение;
- lookup timeout;
- update check недоступен;
- правило пропущено из-за канала.

В обычный лог не писать полностью:

- личные сообщения;
- сообщения почты;
- тексты автоответов;
- суммы переводов;
- полные сообщения чата.

Допустимо логировать:

- длину;
- тип действия;
- хеш или маскированный ник;
- идентификатор подсистемы;
- причину отказа.

# 24. Потоки

## Client thread

На client thread должны выполняться:

- Minecraft UI;
- отправка чата;
- отправка команд;
- изменение screen;
- работа с connection;
- получение списка игроков;
- обновление HUD snapshot.

## Вне client thread

- HTTP-проверка обновлений;
- тяжёлая подготовка данных, если она когда-либо появится.

После async HTTP нельзя напрямую менять Minecraft UI.

Результат передаётся в thread-safe state, а экран открывается из client tick.

## Config

Config обычно используется на client thread.

Не вводить многопоточность без необходимости.
